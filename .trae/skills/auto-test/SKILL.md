# Auto Test — 代码变更后的自动化质量门禁

这是一个专门为本项目（墨迹博客 — Next.js 16 + React 19 + Tailwind CSS 4）定制的自动化测试技能。它能在每次代码变更后快速执行一套完整的质量检查流水线，确保改动不会破坏现有功能。

## 测试理念

本项目没有传统的单元测试框架（Jest/Vitest），因此测试策略采用**实战验证**模式：用真实的构建、真实的 API 请求、真实的浏览器渲染来验证代码质量。这比写 mock 更贴近生产环境，能发现更多实际问题。

## 执行时机

在以下场景完成代码编写后，**必须**运行此测试流水线：

1. 修改了 `app/` 下的任何页面或 API 路由
2. 修改了 `components/` 下的任何组件
3. 修改了 `lib/` 下的业务逻辑
4. 修改了 `data/` 下的 JSON 数据
5. 修改了配置文件（`next.config.ts`、`tsconfig.json`、`package.json`）
6. 用户明确要求测试或验证

## 测试流水线

按照以下顺序逐步执行，每一步都需要确认通过后才进入下一步。如果某一步失败，立即停下来修复，修复后从失败步骤重新执行。

### 第一关：TypeScript 编译检查

这是最基础也是最快的检查，能捕获类型错误、导入缺失、语法错误等问题。

**执行方式：**
```bash
npx tsc --noEmit
```

**通过标准：** 零错误输出，exit code 为 0。

**常见问题处理：**
- 类型不匹配 → 检查接口定义是否与实际数据结构一致
- 找不到模块 → 检查 import 路径是否使用 `@/` 前缀（项目配置了 `@/*` → `./*`）
- 属性不存在 → 检查组件 props 接口是否完整

### 第二关：Next.js 生产构建

这能发现 TypeScript 检查遗漏的问题，如服务端/客户端混用错误、动态导入问题、CSS 构建错误等。

**执行方式：**
```bash
npm run build
```

**通过标准：** 构建成功，所有路由正常编译。检查输出中的路由表确认所有页面都在列表中：
- `○ /` （首页）
- `○ /about` （关于）
- `○ /bookmarks` （收藏）
- `ƒ /blog` （博客列表）
- `ƒ /blog/[slug]` （文章详情）
- 所有 `ƒ /api/*` 路由

**常见问题处理：**
- `"use client"` 缺失 → 使用了 useState/useEffect 等 Hook 的组件必须标记
- 服务端组件引用客户端模块 → 拆分或添加动态导入
- CSS 类名冲突 → 检查 Tailwind 类是否拼写正确

### 第三关：开发服务器启动与 API 冒烟测试

启动开发服务器，对关键 API 接口发送真实请求，验证数据返回格式正确。

**执行步骤：**

1. 检查是否已有开发服务器在运行（查看 terminals 目录），如果没有则启动：
```bash
npm run dev
```

2. 等待服务器就绪（出现 `✓ Ready` 日志），然后运行冒烟测试脚本：
```bash
node .cursor/skills/auto-test/scripts/smoke-test.mjs
```

3. 脚本会自动测试以下接口并输出结果：

| 接口 | 验证项 |
|------|--------|
| `GET /api/health` | 状态码 200，返回 `status: ok` |
| `GET /api/bookmarks` | 状态码 200，返回 `code: 0`，`data` 是数组 |
| `GET /api/poems?count=3` | 状态码 200，返回数据数组 |
| `GET /api/recommend/daily` | 状态码 200，返回推荐列表 |
| `GET /api/posts` | 状态码 200 或因无 GET 实现而预期为 405 |
| `GET /api/meta/dynasties` | 状态码 200，返回朝代元数据 |
| `GET /api/search?q=月` | 状态码 200，返回搜索结果 |

**通过标准：** 所有接口返回预期状态码和数据结构。

### 第四关：页面渲染验证（浏览器自动化）

使用 MCP 浏览器工具访问每个页面，确认能正常渲染、无白屏、无 JavaScript 报错。

**执行步骤：**

对以下每个页面执行浏览器验证：

| 页面 | URL | 检查内容 |
|------|-----|----------|
| 首页 | `http://localhost:3000/` | 能看到"墨·迹"标题、导航栏、页面主体内容 |
| 收藏页 | `http://localhost:3000/bookmarks` | 能看到书签分类列表、各分类下的书签卡片 |
| 博客列表 | `http://localhost:3000/blog` | 能看到文章列表 |
| 关于页 | `http://localhost:3000/about` | 能看到关于内容 |

**每个页面的验证流程：**
1. 使用 `browser_navigate` 访问页面
2. 等待 2-3 秒让内容加载完成
3. 使用 `browser_snapshot` 获取页面快照
4. 检查快照中是否包含预期的关键元素（标题、导航、内容区域）
5. 使用 `browser_console_messages` 检查是否有 JavaScript 错误（忽略 warning 级别）
6. 如果页面出现 loading spinner 超过 5 秒仍未消失，标记为失败

**通过标准：** 所有页面正常渲染，无 JS 错误（warning 除外），无白屏。

### 第五关：数据完整性检查

验证 `data/` 目录下的 JSON 文件格式正确且数据结构合法。

**执行方式：**
```bash
node .cursor/skills/auto-test/scripts/data-check.mjs
```

**检查项：**
- `bookmarks.json`：能正常解析，每个分类有 `id`/`name`/`icon`/`color`/`bookmarks` 字段，每个书签有 `id`/`title`/`url`
- `tangshi.json` / `songci.json` / `yuanqu.json`：能正常解析，数组不为空
- `must_poem.json`：能正常解析
- `like.json` / `likes_state.json`：能正常解析

**通过标准：** 所有 JSON 文件语法正确，关键字段不缺失。

## 快速模式 vs 完整模式

如果用户只做了小改动（比如只改了一个样式或文案），可以跑**快速模式**（跳过第二关构建，只做 TypeScript 检查 + API 测试 + 页面验证）。如果用户要求"完整测试"或改动涉及多个文件/核心逻辑，则运行**完整模式**（全部五关）。

默认使用**完整模式**。

## 错误修复循环

如果测试过程中发现问题：
1. 立即停止后续测试
2. 分析错误原因
3. 修复代码
4. 从失败的那一关重新开始测试
5. 全部通过后输出最终报告

最多循环 3 次自动修复。如果 3 次后仍有问题，停下来向用户汇报所有发现的问题和尝试过的修复方案。

## 注意事项

- 本项目使用 PowerShell 作为 Shell，命令链接使用 `;` 而非 `&&`
- 开发服务器默认在 `http://localhost:3000`，如果端口被占用会使用 3001
- 浏览器测试前需确认 dev server 已在运行
- JSON 数据文件使用 UTF-8 编码
- `content/` 目录下的 Markdown 文件的 frontmatter 必须包含 `title`、`date`、`summary`
